Seldon — Architecture

Telegram / app → FastAPI nodes+edges → SQLite graph → force-directed canvas. Click/expand boxes for detail. 100% drag to pan · scroll/pinch to zoom · click ▸ to expand

📱 Telegram bot

Primary input channel. Any text message becomes a note. Also understands workspace-switch commands and topic: prefixes.

⚙️ FastAPI app — app/main.py

create_app() builds the FastAPI instance (title "Seldon"), mounts /static (frontend) and /uploads, and registers every route. Single global app = create_app() at module bottom is the ASGI entrypoint run by uvicorn app.main:app.
Expand: lifespan startup sequence

@asynccontextmanager lifespan() runs on boot:

  • init_db(session_factory) — creates tables, runs SQLite migrations, backfills workspace_id columns
  • Copies src/uploads (seed images) into the runtime uploads dir if not already present
  • seed_workspace(db) — creates/activates the "humans (default)" workspace with its 9 seed nodes + 9 seed edges, if empty
  • seed_default_user(db) — creates the default account (rioname@gmail.com) and attaches any ownerless workspaces to it
  • start_model_setup(app) — background thread warms the sentence-transformer embedding model (skipped unless preload_embedding_model_on_startup is true)
  • asyncio.create_task(auto_poll_loop(app)) — background Telegram poller (see box below)

Expand: auth model & per-user workspaces

Two parallel paths exist in the route handlers: an anonymous/global path (get_active_workspace(db) — one shared active workspace, the historical default) and a per-user path (token query param → get_user_from_token → get_active_workspace_for_user(db, user)). User.access_token is a secrets.token_urlsafe(32) bearer token; User.password_hash is bcrypt via auth_login/auth_register. New email registrations and new Telegram chat ids both get seed_workspace_for_user() — their own private clone of the "humans (default)" seed graph (per-user workspaces are named u{id}:{name} internally to dodge the global unique-name constraint on workspaces.name).

🔁 auto_poll_loop (background task)

asyncio.sleep(30) loop started in lifespan(). Every 30s, if a bot token is configured, fetches new Telegram updates from the stored offset and ingests them — independent of the manual Poll Telegram button in the app.
Expand: per-chat onboarding

For each update's chat.id, get_or_create_user() looks up or creates a User keyed on telegram_chat_id. A brand-new chat triggers seed_workspace_for_user() and a welcome DM via send_telegram_message() containing a personal graph link: {public_url}/graph?token={access_token}. Any exception in the loop body is swallowed (except Exception: pass) so one bad update can't kill the poller.

📥 telegram_ingest.py

ingest_telegram_update() — the core parsing pipeline for every incoming Telegram message, text or /poll batch alike.
Expand: parsing order
  1. Dedup on source_event_id = "telegram:update:{update_id}" against IngestionJob → outcome duplicate
  2. Extract text/caption; empty → IngestionJob(status="ignored")
  3. extract_explicit_node_type() — TOPIC_PREFIX_PATTERN (^topic:\s*) forces type="topic"
  4. extract_workspace_switch_command() — three regexes: switch to X, switch workspace to X, switch workspace to timeaware X → outcome switched_workspace, no node created
  5. extract_tags_from_text() — HASHTAG_PATTERN = (?<!\w)#([A-Za-z][A-Za-z0-9_-]*), then strip_tags_from_text() removes them from raw_text
  6. classify_telegram_text(raw_text) by character length (see Node types box) unless an explicit type was set
  7. prepare_node_content() builds normalized_text + metadata (normalization, linker_tags)
  8. Node row created with source="telegram", author = Telegram username, telegram_message_id = "{chat_id}:{message_id}"
Expand: offset & polling

poll_telegram_updates() calls Telegram's getUpdates with limit=telegram_poll_limit (default 25) and timeout=1. The next offset (last update_id + 1) is persisted in AppState under key telegram_poll_offset via store_telegram_offset() — survives restarts.

Expand: SQLite auto-migration

database.py: _migrate_sqlite_schema() runs on every boot — inspects existing columns via SQLAlchemy's inspect() and ALTER TABLE ... ADD COLUMNs anything missing (e.g. backfilling workspace_id across 13 tables, users.email/password_hash, workspaces.type/embed_token/user_id). _backfill_workspace_ids() then points every orphan row at a "maker graph" default workspace. This is how the schema evolved live against a single SQLite file without Alembic.

🧮 Embedding + Link job queues

Every node create/update enqueues both an EmbeddingJob and a LinkJob (enqueue_embedding_job, enqueue_link_job in main.py).
Expand: embedding_ops.py

embedding_input_for_node() = normalized_text or raw_text. content_hash = sha256("{model_name}\n{text}") dedupes — identical content under the same model reuses an existing embedding row instead of recomputing (even cross-node: cached_embedding lookup clones the vector). Model: sentence-transformers/all-mpnet-base-v2 (default), loaded lazily via SentenceTransformer and cached in _MODEL_CACHE. process_pending_embedding_jobs() batches up to embedding_batch_size (default 10) pending jobs.

Expand: linker_ops.py — tag-based auto linking

process_pending_link_jobs() pulls each node's internal keyword/concept tags via shared_internal_tags_for_node() (reverse lookup on internal_tag_memberships), finds other nodes sharing at least one tag, then runs run_tag_matcher (see Edge creation box) against just those candidates — not the whole workspace — before creating Edge rows directly with created_by="linker". SYMMETRIC_RELATIONS = {"similar_to", "contradicts"} are checked in both directions to avoid duplicate edges.

🪄 edge_creation_ops.py

Five named functions behind POST /edge-creation/{function_name}, triggered from the Advanced tab or the Generate Edges button. EDGE_CREATION_FUNCTIONS = tag_matcher, embedding_matcher, llm_matcher, llm_debator, hub_matcher.
Expand: tag_matcher
Extracts/reuses "internal tags" (8 keywords + 7 concepts) per node via Ollama (ollama_tag_model = "qwen2.5:3b-instruct", prompt frames the task as "designing external brain application... for 7 astronauts going to mars"), falling back to _heuristic_extract_internal_tags() (token-frequency + bigram/trigram phrases) if Ollama is unavailable or use_ollama_for_internal_tags=False. Score = shared tag count / smaller tag-set size.
Expand: embedding_matcher & llm_matcher/debator

embedding_matcher uses a deterministic hash-based pseudo-embedding (_hash_embedding() — md5 of each token bucketed into a 64-dim vector with a sign bit), cosine similarity, threshold 0.58 default.

llm_matcher (threshold 0.45) and llm_debator (threshold 0.42) are explicitly labelled "Heuristic ... placeholder" in code — they blend the same hash-similarity (72%/70% weight) with lexical Jaccard overlap (28%/30%) rather than calling a real LLM; llm_debator additionally fabricates pro/con/judge argument strings for the UI's debate summary.

Expand: edge type decision & hub_matcher

_edge_type_for_pair() picks from DEFAULT_EDGE_TYPES = similar_to, supports, contradicts, expands, led_to, belongs_to_topic: a topic-typed node forces belongs_to_topic; CONTRAST_WORDS (but/however/instead/except/unless/yet) can force contradicts; similarity ≥0.7 → similar_to; lexical overlap ≥0.24 with a length gap >50 chars → expands; else supports.

hub_matcher groups nodes by shared top-4 concepts into ExperimentalHub rows (persisted, signature = "hub_matcher:{label}") — proposes clusters, not pairwise edges.

🖥️ Frontend — app.js (graph canvas)

Vanilla JS + hand-rolled SVG, no framework, served from src/frontend and mounted at /static; index.html is the /graph page.
Expand: force-directed layout constants
app.js: forceLayout(nodes, edges, width, height), 320 simulation iterations:
ConstantValue
repulsion28000
attraction0.018
centerStrength0.004
damping0.82
minDist (repulsion floor)240

Pairwise repulsion falls off with 1/distance²; edges act as springs pulling toward idealLength. A separate polarLayout() (orbital rings) and timelineLayout() (horizontal time axis, used only for time-aware workspaces) are also defined.

Expand: node cards, dragging, saved positions

Node card sizing: width 178px (206px if text >240 chars), image thumbnail adds IMAGE_HEIGHT = 120px at the top, WhatsApp-style. Dragging a node writes to an in-memory nodePositions map and persists via metadata_json.ui_position (PATCH to /nodes/{id}) so layout survives a refresh — forceLayout() only runs for nodes that don't already have a stored/dragged position.

Edge curves sag based on distance: sag = clamp(distance * 0.15, 20, 54) px. Edge weight slider in the UI is 0–100; sent to the API divided by 100 (weight/100) since the backend stores 0–1 floats.

Expand: other frontend pages
  • landing.html — marketing/home page at /
  • advanced.html + advanced.js — raw API forms for the 5 traversal methods and 5 edge-creation methods, hits the endpoints directly and shows JSON
  • embed.html / embed.js / embed.css — read-only embeddable graph view, gated by workspace_id + embed_token (no cookies/auth)

🧭 traversal_ops.py

BFS-style traversal over the Edge/Node graph, used by path tracing, Advanced tab, narrative generation, and article outline planning.
Expand: fetch_neighbors & collect_subgraph

fetch_neighbors() — direction incoming|outgoing|both, optional edge_type filter, sorted by weight desc. collect_subgraph() does a weighted BFS from a root node up to depth hops (default 2) and limit nodes (default 12), computing a path_score per node = product of edge weights along the best path found (weight floor 0.01 to avoid zeroing out).

build_outline_sections() groups the traversed subgraph by the edge relation connecting each node back to the root, labelling sections via RELATION_SECTION_TITLES (e.g. supports → "Supporting Ideas", contradicts → "Counterpoints", belongs_to_topic → "Topic Connections").

📖 narrative_ops.py + article_ops.py

Both consume a collect_subgraph() result and talk to local Ollama; hidden from the deployed app since Ollama isn't available on Railway.
Expand: narrative generation
build_narrative_prompt() lists every traversed node (id, depth, path_score, type, text) and edge (from→to, type, weight), then asks the model for an exact N-paragraph (default 2) narrative in the voice of someone narrating the evolution of the user's thought — explicitly told not to mention node ids or "the graph". Model: ollama_narrative_model = "qwen2.5:3b-instruct" via POST {ollama_base_url}/api/generate.
Expand: article drafts
create_article_draft() builds an outline_json from build_outline_plan() (traversal + outline sections) and stores it alongside a freeform content_markdown field; every edit calls create_article_draft_version() first, mirroring the node-versioning pattern (node_versions / article_draft_versions, both reason-tagged snapshots).

🗂️ workspace_ops.py

Two workspace types: general (force-directed, no time axis) and time_aware (horizontal timeline, requires a time_label per node). Default seed workspace name: "humans (default)"; DB-level default name: "maker graph" (DEFAULT_WORKSPACE_NAME).
Expand: active-workspace pointer & per-user naming

Active workspace is tracked in AppState: key "current_workspace" for the anonymous/global path, or "current_workspace:{user.id}" per logged-in user. Per-user workspaces created via get_or_create_workspace_for_user() are internally named "u{user_id}:{display_name}" to satisfy the global unique constraint on workspaces.name, with the human-readable name kept in metadata_json.display_name (get_workspace_display_name() prefers it).

🚢 Deployment

Dockerfile: python:3.12-slim, copies src/app → /app/app, src/frontend → /app/frontend, src/uploads → /app/seed-uploads. Runs uvicorn app.main:app --host 0.0.0.0 --port 8000.
Expand: railway.toml
Deploys on Railway with restartPolicyType = "on_failure", max 3 retries. Env vars: DATABASE_URL = sqlite:////data/twitter_poster.db, TWITTER_POSTER_PUBLIC_URL = https://seldon.railway.app, UPLOADS_DIR = /data/uploads — persistent volume mounted at /data outlives container restarts (unlike the ephemeral filesystem elsewhere in the image).
